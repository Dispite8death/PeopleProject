ПОКЕМОН — ЗАДАНИЕ CODEX НА ПЕРВЫЙ ЭТАП
Окружение Windows, интерфейс и основа для подключения моего бэкенда

КОНТЕКСТ И ГРАНИЦЫ РАБОТЫ

Начинаем новый университетский проект с пустой папки: готового кода нет. Рабочее название — «ПОКЕМОН». Предварительная расшифровка: «Поиск и отсеивание кандидатов для единовременных мероприятий отдельного назначения». Это самостоятельная платформа заявок преподавателей о помощи и мероприятиях. Она не занимается распределением аудиторий и созданием расписания.

Твоя задача — установить и проверить локальное окружение на моём Windows-компьютере, создать структуру проекта и полностью сделать фронтенд с демонстрационными данными. Бэкенд я буду писать самостоятельно. Мне нужна удобная основа, к которой можно постепенно подключать мои серверные методы. Не реализуй вместо меня серверные правила записи, авторизацию, рассылки, добор и интеграции. Технический PHP-каркас, вывод шаблонов, безопасное подключение конфигурации и проверка соединения с БД входят в твой этап.

Общайся по-русски. Сначала проверь рабочую папку, инструкции репозитория и среду. Если обнаружишь существующий код или мои изменения, сохрани их. Не используй файлы другого моего проекта как основу без моей просьбы. Не публикуй сайт и не выполняй push.

1. ТЕХНИЧЕСКИЕ РЕШЕНИЯ НА СТАРТ

Подтверждено: разработка на Windows, PHP и nginx; фронтенд делегирую тебе, бэкенд пишу я.

Стартовые технические предложения, которые можно использовать до моих уточнений:
• Нативный Windows, nginx + PHP NTS x64 через php-cgi/FastCGI. Это локальная среда разработки, не готовая конфигурация серверного развёртывания университета.
• MariaDB с InnoDB, подключение из PHP через PDO и pdo_mysql.
• Обычные PHP-шаблоны/частичные шаблоны, HTML, CSS и JavaScript ES modules. На этом этапе не требуются Laravel, React, Vue или сложная цепочка сборки.
• Светлый аккуратный интерфейс на русском, адаптивный для компьютера и телефона. Дизайн выбери самостоятельно.

Эти предложения не означают, что я уже выбрал всю архитектуру бэкенда. Сделай интерфейс так, чтобы замена источника данных не требовала переписывать страницы. Не добавляй Docker/WSL как обязательное условие запуска; если нативное окружение окажется заблокировано, объясни конкретную причину и доступные варианты.

Источники для проверки установки:
https://nginx.org/en/docs/windows.html
https://www.php.net/manual/en/install.windows.manual.php
https://www.php.net/manual/en/features.commandline.options.php
https://www.php.net/manual/en/ref.pdo-mysql.php
https://mariadb.com/docs/server

Используй актуальные поддерживаемые сборки с официальных источников, проверь архитектуру и зависимости и запиши реально установленные версии. Не копируй версии наугад из этого задания. У nginx для Windows есть ограничения масштабирования: для локальной разработки это допустимо, производственное размещение обсудим отдельно.

2. ОКРУЖЕНИЕ

• Проверь наличие nginx, PHP, MariaDB/MySQL, необходимые расширения и занятые порты. Сохрани уже установленные сервисы и их данные. При конфликте выбери отдельные порты/конфигурации для этого проекта.
• Установи недостающие компоненты, настрой PHP и соединение nginx с FastCGI. Для Windows используй php-cgi.exe; PHP-FPM относится к варианту с Linux.
• Создай отдельную локальную БД и пользователя с правами только на неё. Приложение не должно постоянно работать от root. Не создавай окончательную предметную схему БД до её проработки со мной: на этом этапе достаточно проверить соединение и кодировку utf8mb4.
• Настройки и пароли держи вне public и вне Git. Добавь образец конфигурации без секретов. Подключение к БД вынеси в небольшой понятный модуль. Не отдавай браузеру .env, конфигурацию, исходники служебных скриптов, дампы и логи.
• Локальные HTTP/FastCGI/БД слушают loopback. Для начала достаточно адреса вида http://127.0.0.1:8080; при занятом порте подбери свободный и запиши его. Настройка домена и публичного доступа сейчас не требуется.
• Создай PowerShell-скрипты запуска, остановки и проверки состояния. Они должны проверять занятость портов, не создавать дубли процессов и останавливать только экземпляры этого проекта, а не все nginx/PHP/БД на компьютере. Уже работающие сторонние службы не останавливай.
• Проверь nginx-конфигурацию, выполнение PHP через HTTP и подключение PHP к БД. Диагностику с паролями или полным phpinfo не оставляй доступной через сайт.
• В README опиши запуск после перезагрузки, расположение конфигурации и логов, установленные версии. Скрипты должны корректно обрабатывать пути с пробелами. Бинарники, каталоги данных БД, логи и локальные настройки исключи из Git.

3. ПОДТВЕРЖДЁННЫЕ ПРАВИЛА БУДУЩЕГО ПРОДУКТА

Роли: преподаватель/автор заявки, куратор группы, староста группы, студент, администратор. У одного человека могут совмещаться роли; староста остаётся студентом, а преподаватель может быть куратором. Учитывай это в навигации и предложении модели данных.

Преподаватель создаёт заявку: название, описание, дата/время начала и окончания, тип «помощь» или «мероприятие». Место проведения можно предложить как необязательное поле.

Автор выбирает аудиторию:
1) свободные в указанный промежуток по учебному расписанию;
2) конкретные группы независимо от наличия пар;
3) все группы.

Затем приглашение сначала получает куратор каждой выбранной группы. Только если куратора у группы нет, решение принимает её староста. Отказ куратора не означает перенаправление старосте. Ответственный разрешает или отклоняет распространение заявки своей группе. Его согласие не записывает студентов на мероприятие.

После согласования приглашение поступает студентам этой группы. Каждый отвечает самостоятельно: согласие или отказ. Автор видит решения представителей групп и отдельный подробный список ответов студентов.

Участие в двух пересекающихся по времени заявках запрещено. Уже принятые мероприятия учитываются независимо от выбранного режима рассылки. Если студент принимает одну заявку, пересекающиеся ожидающие приглашения отклоняются. Автоматический отказ и ручной отказ отображаются автору одинаково, без причин, пометок «занят» и раскрытия другого мероприятия. Это относится и к будущим ответам API, а не только к скрытию поля на экране.

Лимит участников необязателен. Если его нет, принимаются все подходящие согласившиеся. Если указан, места занимаются в порядке успешного подтверждения на сервере. При заполнении лимита набор закрывается и участникам рассылки отправляется уведомление. Само мероприятие при этом не считается завершённым.

Студенту необходимо позволить отменить согласие. Для освободившихся мест нужен автоматический добор в рамках той же заявки, чтобы автору не приходилось каждый раз создавать новый набор.

На первом этапе уведомления планируются по электронной почте. Источники адресов — университетские данные студентов, в перспективе СДО/ЛК. Для MVP предусмотрено ручное администрирование пользователей и групп. Рассылку и обработку настоящих адресов сейчас не реализуй: нужны экраны, данные для демонстрации и точки подключения моего бэкенда.

4. ВОПРОСЫ, КОТОРЫЕ ЕЩЁ НЕ УТВЕРЖДЕНЫ

Не придумывай окончательные правила за меня. Запиши отдельным списком решения для следующего этапа:
• источник и формат учебного расписания; импорт или ручное ведение;
• точный механизм автоматического добора, сроки ответа и окончание набора;
• политика изменений времени мероприятия после согласований и записи участников;
• окончательная авторизация, выдача учётных записей, восстановление доступа;
• адреса отправителя, SMTP и размещение сервера университета;
• доступ к платформе вне университетской сети;
• правила удаления/архивирования пользователей, заявок и истории.

Добровольный резерв, предложение места по очереди с новым подтверждением и ограниченным временем ответа — предварительная идея, а не утверждённое требование. Её можно показать отдельным демонстрационным сценарием, но не делать обязательной частью контракта без моей дальнейшей команды.

Сейчас не нужен рабочий импорт расписания. В интерфейсе должно быть понятно, когда расписание не подключено; отсутствие данных не равно отсутствию пар. Если показываешь фильтр свободных студентов на моках, обозначь, что это демонстрационные данные.

MAX — последующий этап. Идея: студент в кабинете получает числовой код, вводит его боту и привязывает аккаунт мессенджера к своему профилю; после привязки уведомления идут в MAX вместо почты. Возможности API, срок действия и защита кода ещё предстоит проверить. Сейчас не делай бота и не изображай привязку работающей.

5. ЧТО НУЖНО СДЕЛАТЬ ВО ФРОНТЕНДЕ

Общий каркас: название, навигация по доступным ролям, профиль, уведомления, понятные состояния загрузки/ошибки/пустого списка. Для мобильного экрана используй удобную навигацию и карточки или прокручиваемые таблицы с доступными действиями. Не используй персонажей и фирменные изображения франшизы Pokémon: это название университетского проекта.

Кабинет преподавателя:
• список собственных заявок, поиск и фильтры по статусу/дате;
• форма создания/редактирования с названием, описанием, временем, аудиторией и необязательным лимитом;
• выбор групп с поиском; явное различие «все группы», «выбранные» и «свободные по расписанию»;
• карточка заявки с числом подтверждённых участников, лимитом/отметкой «без ограничения» и состоянием набора;
• отчёт по согласованию рассылки каждой группой;
• отдельная вкладка или окно ответов студентов с фильтрами по группе и ответу, без причин отказов;
• состояния «ожидает согласований», «идёт набор», «места заполнены», «нужен добор», «отменено», «завершено». Не смешивай жизненный цикл заявки, согласования и ответы студентов в одно поле.

Кабинет куратора/старосты:
• входящие заявки для его групп;
• просмотр условий и две ясные кнопки разрешения/отказа в рассылке;
• история решений и отметка, для какой группы принято решение;
• при наличии нескольких ролей — доступ к соответствующим разделам без потери собственного студенческого кабинета.

Кабинет студента:
• список приглашений и подробности заявки;
• принять/отказаться, подтверждение отмены своего участия;
• отдельный список принятых мероприятий;
• понятные состояния «ожидает ответа», «участие подтверждено», «отказ», «мест больше нет», «мероприятие отменено»;
• корректная реакция на ответ сервера, если последнее место уже заняли или возникло пересечение: клиентская проверка сама по себе ничего не гарантирует.

Административный раздел для меня:
• таблицы и формы пользователей: имя, email, группа/связи с группами, роли;
• таблицы и формы групп, назначение куратора и старосты;
• понятный показ отсутствующего ответственного;
• ручное добавление и редактирование демонстрационных записей. Университетские интеграции и реальные учётные записи пока не создавать.

Форма входа может быть макетом с email и паролем; это временная гипотеза UI, не окончательная схема авторизации. Отдельно сделай переключатель демонстрационных пользователей/ролей. Он должен быть явно помечен и технически отделён от будущего настоящего входа.

Покажи несколько реалистичных вымышленных групп, преподавателей и студентов. Нужны сценарии пустого списка, обычного набора, заполненного лимита, отказа группы, отмены участия и ошибки. В деморежиме основные кнопки, формы, фильтры и переходы должны работать. Не отправляй реальную почту и не используй настоящие персональные данные.

6. ПОДКЛЮЧЕНИЕ К МОЕМУ БЭКЕНДУ

• Вынеси работу с данными в отдельный JS-модуль с единым интерфейсом. Создай демонстрационный источник данных и отдельно заготовку HTTP-источника. Не разбрасывай fetch по обработчикам отрисовки.
• Деморежим должен быть явным. При ошибке реального API нельзя незаметно подставлять моки и показывать успешную запись.
• Основной интерфейс должен отображать итоговое состояние и доступные действия, полученные от сервера. Количество мест, права и запреты всегда окончательно проверяет будущий бэкенд.
• Подготовь небольшой docs/api-contract.md: предложенные маршруты, методы HTTP, поля запросов и ответов, ошибки, форматы дат/идентификаторов, смысл статусов и разрешённые действия. Это проект контракта для моего согласования, а не повод писать весь backend.
• Отдельно опиши сущности: пользователь, группа, роли/связи, заявка, согласование группы, приглашение и ответ/участие. Предложи структуру БД документом; не создавай окончательные таблицы автоматически.
• В JSON различай отсутствие лимита (null) и положительный лимит; 0 не должен молча означать неограниченный набор. Не смешивай display-текст и машинные коды статусов.
• Укажи часовой пояс и форматы времени; первоначальная зона отображения — Asia/Magadan, данные API должны иметь однозначные временные значения. Окончательную серверную политику хранения опиши как предложение.
• Запиши сценарии, которые я должен обеспечить на сервере: атомарное занятие последнего места, повторная проверка пересечений, отсутствие двойной записи при повторном запросе, исключение неподтверждённых групп из рассылки, одинаковое раскрытие отказов без причин. Клиентские моки не считаются реализацией этих гарантий.

7. КАЧЕСТВО И ГОТОВНОСТЬ ЭТАПА

Дизайн должен быть цельным и пригодным для дальнейшего использования: читаемые размеры текста, ясные подписи, заметные статусы, понятные формы, доступная клавиатурная навигация и фокус. Пользовательский текст вставляй безопасно; не исполняй HTML из названий и описаний. Стили и общие компоненты переиспользуй.

Проверь в браузере основные экраны на настольной и мобильной ширине. Пройди сценарий: преподаватель создаёт демонстрационную заявку → представитель группы разрешает рассылку → студент принимает → в отчёте обновляется результат. Проверь случай заполненного лимита и отмену участия как демонстрацию UI; явно укажи, что серверные гарантии ещё не реализованы.

Проверь ошибки JS, PHP-синтаксис, сетевые ошибки, повторные нажатия, пустые данные, длинные названия и валидацию дат/лимита. Тестируй существенные сценарии; не заполняй проект формальными тестами, повторяющими разметку.

Передай:
1) работающий локальный адрес и команды запуска/остановки;
2) готовые исходники интерфейса и технического каркаса;
3) конфигурацию nginx/PHP, пример конфигурации БД без пароля;
4) README на русском с установленными версиями и расположением файлов;
5) проект API-контракта и предложение сущностей БД;
6) короткий список точек, куда я подключаю свой backend;
7) отчёт о реально выполненных проверках и оставшихся вопросах.

Работай автономно в пределах этого этапа. Рутинные решения по установке, вёрстке, цветам и структуре файлов принимай сам. Задавай вопрос только при настоящем блокере. Не останавливайся на плане или одном красивом экране: закончи окружение и перечисленные интерфейсы. При этом не подменяй мою часть проекта полноценной реализацией бэкенда.
