# Проект API-контракта ПОКЕМОН

Это предложение для согласования. Серверные методы, авторизация и бизнес-гарантии не реализованы. Сейчас nginx возвращает 501 на `/api/`; демо использует локальное хранилище браузера. Ошибка настоящего API никогда не подменяется моками.

## Общие соглашения

Базовый путь `/api/v1`. JSON UTF-8. Идентификаторы — непрозрачные строки, не числа для арифметики. Даты — RFC 3339 с явным смещением или `Z`, например `2026-11-16T10:00:00+11:00`. Интервалы полуоткрытые `[начало, конец)`: конец одного может совпадать с началом другого. Отображение — `Asia/Magadan`. Хранение UTC и отдельного идентификатора зоны предлагается, окончательная политика требует согласования.

Успех: `{ "data": ... }`. Ошибка: `{ "error": { "code": "CAPACITY_FULL", "message": "Мест больше нет", "fields": {} } }`. `fields` — объект ошибок формы по именам полей. Ни трассировок, ни SQL, ни персональных сведений другого участника в ответе быть не должно.

Ожидаются HTTP 200 для чтения/изменения, 201 для создания, 400/422 для валидации, 401 без сессии, 403 без полномочий, 404 для недоступного ресурса, 409 для конфликта состояния, 503 для недоступности зависимостей. Изменения возвращают итоговый объект. Пагинацию больших списков нужно согласовать перед промышленным использованием: текущий демонстрационный контракт возвращает небольшие полные массивы.

`Idempotency-Key` передаётся HTTP-адаптером при изменениях. Сервер должен хранить результат логической операции и проверять соответствие ключа телу/пользователю. Сам ключ не заменяет уникальные ограничения и транзакции. Авторизация и защита от CSRF будут добавлены вместе с выбранной схемой входа. Адаптер передаёт `credentials: same-origin`; это не готовая реализация авторизации.

## Статусы и действия

- `request.lifecycle`: `active`, `cancelled`, `completed`. Заполнение мест не переводит событие в `completed`.
- `request.recruitment`: `awaiting_approvals`, `open`, `full`, `refill`. Это вычисляемое состояние набора, а не решение группы или ответ студента.
- `request.status`: удобный вычисляемый код для фильтра/подписи: сначала конечный lifecycle, иначе recruitment.
- `groupApproval.decision`: `pending`, `approved`, `rejected`.
- `invitation.response`: `pending`, `accepted`, `declined`, `withdrawn`. `withdrawn` доступен самому участнику; в отчёте автора отображается как `declined`.
- `invitation.state`: состояние для кабинета участника, также может быть `full`, `cancelled`, `completed`.
- `allowedActions` содержит только разрешённые текущему пользователю действия. Сервер обязан повторно проверить их при выполнении команды. Отсутствие кнопки не является проверкой полномочий.

`limit: null` означает отсутствие лимита. Положительное целое — лимит. Ноль, отрицательное, дробное значение и строка не эквивалентны null и должны отклоняться. Число подтверждённых участий возвращается как `participantCount`.

## Маршруты, соответствующие HTTP-адаптеру

### GET /workspace

Возвращает `viewer`, `groups`, `users`, `requests`, `approvals`, `invitations`, `schedule`, `notifications`, `mode`.

`viewer`: `{id,name,email,roles,groupId}`. Роли — массив кодов `teacher`, `curator`, `leader`, `student`, `admin`. Староста одновременно студент. Связи кураторов с группами находятся в группах; на следующем этапе их можно нормализовать.

`requests` содержит собственные заявки автора. `approvals` — только решения групп, за которые отвечает пользователь. `invitations` — только его личные приглашения. Полный `users` доступен только администратору, иначе пустой массив. `groups` — минимально необходимый справочник, его объём нужно ограничить правами на сервере. `schedule`: `{connected:false,demoAvailable:false}` для неподключённого настоящего расписания. Не трактовать это как отсутствие занятий.

Элемент `requests`:

```json
{
  "id":"request-id", "authorId":"user-id",
  "title":"Подготовка выставки", "description":"Описание задачи",
  "type":"help", "location":"Библиотека",
  "startsAt":"2026-11-16T10:00:00+11:00", "endsAt":"2026-11-16T12:00:00+11:00",
  "audience":"selected", "groupIds":["group-id"], "limit":12,
  "lifecycle":"active", "recruitment":"open", "status":"open",
  "participantCount":3, "approvalsCount":1, "groupsCount":2,
  "needsRefill":false, "allowedActions":["edit","cancel","complete"]
}
```

`type`: `help` либо `event`. `audience`: `selected`, `all`, `free`. `groupIds` — фактические выбранные группы на момент создания. Список для `free` вычисляет сервер по расписанию. `demoSchedule` — исключительно поле локального демо, реальному серверу его принимать как основание доступа нельзя.

Элемент `approvals`: `{id,requestId,groupId,decision,decidedBy,request,allowedActions}`. Действия: `approve`, `reject`.

Элемент `invitations`: `{id,requestId,userId,groupId,response,state,request,allowedActions}`. Действия: `accept`, `decline`, `withdraw`. `request` — безопасное представление заявки для этого участника, без списков других студентов.

### GET /requests/{id}

Возвращает `{request,author,approvals,responses}`. `author` — отображаемое имя. Автор видит согласования и ответы; для представителя и приглашённого студента массивы чужих ответов пусты. Сервер проверяет доступ к самой заявке.

Согласование в отчёте: `{id,requestId,groupId,decision,decidedBy,responsibleName}`. Отсутствие ответственного — `responsibleName: null`.

Ответ в отчёте автора: `{id,userId,name,groupId,response}`. Только `pending`, `accepted`, `declined`. **Никаких `reason`, `busy`, `automatic`, ссылок на другие мероприятия или различающихся текстов ручного и автоматического отказа.** Это правило формы ответа API, а не маскировка в CSS.

### POST /requests

Тело: `{title,description,type,location,startsAt,endsAt,audience,groupIds,limit}`. Автор определяется сессией, не полем клиента. Название 1–160 символов, описание 1–5000, конец строго позже начала. Для selected требуется хотя бы одна действующая группа. Для free без подключённого расписания — `SCHEDULE_UNAVAILABLE`. Возвращается созданная заявка, 201. Создаются ожидающие согласования групп, но не студенческие согласия.

### PATCH /requests/{id}

На текущем этапе форма передаёт только `{title,description,location,limit}`. Лимит не может быть меньше уже подтверждённого количества. Изменение времени/аудитории после публикации заблокировано в макете, пока пользователь не утвердит правила пересогласования.

### POST /requests/{id}/cancel и /requests/{id}/complete

Тело `{}`. Проверить автора и допустимость перехода. Возвращается заявка с новым lifecycle. Отмена закрывает все действия над участием. Завершение — отдельная явная операция автора.

### POST /group-approvals/{id}/decision

Тело `{decision:"approved"}` или `{decision:"rejected"}`. Отвечает куратор, если он назначен, иначе староста. Отказ куратора не вызывает передачу старосте. Одобрение разрешает создание приглашений студентам только этой группы и не записывает их автоматически. Возвращается согласование.

### POST /invitations/{id}/response

Тело `{action:"accept"|"decline"|"withdraw"}`. Возвращается обновлённое представление приглашения. Повторное успешное принятие одного приглашения идемпотентно. После изменения фронтенд перечитывает workspace. Состояние занятых мест и пересечений проверяется внутри серверной транзакции.

Коды конфликтов: `CAPACITY_FULL`, `TIME_CONFLICT`, `STATE_CHANGED`. Причину пересечения можно сообщить только самому студенту; она не входит в ответ автору заявки. `NOT_FOUND`, `FORBIDDEN`, `VALIDATION_ERROR`, `SCHEDULE_UNAVAILABLE`, `NETWORK_ERROR`, `INVALID_RESPONSE` обрабатываются интерфейсом без ложного успеха.

### POST /admin/users, PATCH /admin/users/{id}

Тело `{name,email,roles,groupId}`. Возвращает пользователя. Проверить администратора, уникальность нормализованного email, совместимость ролей и группы. Назначение старостой требует роли студента. Существующую связь ответственного нельзя оставлять с несовместимой ролью: сначала изменить назначение в группе.

### POST /admin/groups, PATCH /admin/groups/{id}

Тело `{name,faculty,curatorId,leaderId}`. Возвращает группу. Идентификаторы ответственных могут быть null. Староста должен состоять в этой группе; куратор должен иметь соответствующую роль. Новую группу сначала создают, затем добавляют её студентов и назначают старосту.

## Обязательные серверные гарантии следующего этапа

1. Атомарное занятие последнего места: блокировка/транзакция и повторный подсчёт, с проверкой всех конкурентных запросов.
2. Повторная проверка временных пересечений принятых мероприятий независимо от режима аудитории и учебного расписания. Учесть изменение/отмену события в той же модели согласованности.
3. Уникальное участие на пару пользователь–заявка, идемпотентные команды, защита от повторной отправки и гонки из двух вкладок.
4. Только одобренные группы участвуют в распространении. Проверка действующего ответственного на сервере.
5. Единое внешнее представление отказов без причины. Приватные основания нельзя включать в сериализацию автора и общие уведомления.
6. При заполнении лимита закрыть набор и поставить уведомление в надёжную очередь, не завершать мероприятие.
7. Отмена согласия освобождает место. Конкретный механизм автоматического добора, сроки и правила резерва ещё не утверждены; клиент показывает `refill`, но не определяет серверную очередь.

Моки демонстрируют поведение одной вкладки и не доказывают ни одну гарантию конкурентного сервера.
